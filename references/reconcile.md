# 入库回读与断点处理

用户已授权录入这批资料时，例行回读、诊断以及有明确来源的缺漏补齐属于同一工作；直接推进到本批验收，不只提出下一步。沿用原商品、SKU 和请求键，未知写入先查状态。

## 先确定实际状态

从本批回执取产品 ID、内部编号、供应商 ID 和文本 SKU。用当前员工 MCP 读取：

1. `enterprise_product_edit_snapshot`：正式记录、当前版本及 `supplierSku` 是否一致。
2. `enterprise_product_suppliers`：同一产品下，指定供方与精确 SKU 的关联 ID、版本及来源。
3. `enterprise_supplier_products`：反查关联产品，按总数翻页，核对同一内部编号；不只看第一页。
4. `enterprise_product_search`：精确 SKU 是否命中同一产品。搜索命中不能替代前面的正式记录与关系回读。

需要确定身份及结构化结果时，可在同一员工电脑执行本 Skill 的只读工具。它读取既有 `yona_enterprise` 配置和本人会话，使用已安装的企业客户端，不输出凭据、不修改服务或数据：

```powershell
python <Skill目录>/scripts/verify_import.py --product-id <实际产品ID> --supplier-id <实际供方ID> --sku <原SKU> --expected-code <原内部编号>
```

退出码 0 仅表示当前员工身份下，这个产品字段、关联、供方反查和搜索一致。退出码 2 表示待处理；保留 JSON 中的具体检查和错误码。工具不验证另一账号或后台浏览器，不把它称为全链路已完成。没有本机 Python 时沿用员工安装包的独立 Python。

## 按失败环节继续

| 实际回读 | 下一步 |
|---|---|
| 有候选、无正式产品 | 核对原候选状态、字段、版本和用户授权；继续确认原候选，不再 stage 同一条 |
| 正式产品有、SKU关联无 | 读取当前关系，按真实来源用 `enterprise_supplier_sku_save` 补到原产品，再做双向回读 |
| SKU已指向另一产品 | 核对两条的源身份；不能强行解绑或新建第三条来绕过冲突 |
| SKU关系有、产品主SKU字段不同 | 先区分多SKU与录入遗漏；不能为了凑校验把另一个已确认的主SKU覆盖掉 |
| 产品/关系均有、搜索无 | 检查权限、分页及现有索引状态；报告具体环节，不重复入库掩盖索引问题 |
| 当前员工四项均有、后台看不到 | 核对后台与MCP的实际账号、租户、过滤条件和部署入口，再打开原产品详情 |
| 401/403/404 | 保留具体接口/工具和错误码；404可能表示不可见，不能直接推断记录不存在 |

厂家档案的管理权限与产品逐记录 ACL 不同。后台 `admin` 也不自动绕过所有者/共享 ACL；不能因为厂家可见就认定它的每条产品都对当前账号可见。账号不同时，先由同一员工账号验证。如果需要让指定管理账号维护，由产品所有者通过已有共享接口或表单设置具体用户/部门，并保留已有授权；未经明确范围不自动向所有人、整个部门开放，也不开放报价、客户、原件等额外内容。

完成后报告“本轮实际回读”的产品/供方/关联 ID、SKU、版本、来源、当前身份、搜索和后台可见性。未测试的另一账号、图片缺失及未执行的官网发布分别保留状态。不能把缺图商品写成图库完成，也不能用官网公开发布解决内部共享问题。
